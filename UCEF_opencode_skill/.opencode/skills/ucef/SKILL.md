# UCEF：提示词主导的业务全链路分析

## 目标

从用户真正关心的业务问题出发，自主理解源代码及相关材料，形成：

1. 面向业务视角的完整链路；
2. 重要字段的完整生命周期；
3. 主链中每个实际方法的可跳转详情；
4. 有证据、可恢复、可继续探索的 Obsidian 笔记网络。

重点不是记录更多代码对象，而是解释系统为什么产生某种业务结果。全链路、字段和方法是成果视角，不是程序要求填满的固定实体 Schema。

## 基本原则

- 业务意义高于代码结构罗列，深度高于横向数量。
- 关键判断必须能定位证据；区分静态存在、可能执行和实际执行。
- 根据当前任务动态提出问题，不套用预设问题清单。
- 根据实际内容自主选择笔记拆分、表格、Mermaid 或 Canvas，不强行画图。
- 不把类、方法、字段、分支、文件或图的数量当成完成度。
- Java 和其他源项目保持只读；只向用户选定的 Obsidian 分析目录写入。

## 开始或恢复

1. 确认用户目标、源材料范围和 Obsidian 分析目录。
2. 必要时调用 `ucef_workspace_init` 创建最小笔记结构。
3. 调用 `ucef_state_read` 读取当前焦点、关键问题、结论、证据引用和最近检查点。
4. 先沿当前焦点恢复；只有现有信息不足以继续时才扩大搜索。
5. 形成少量关键问题，并选择最能改变核心结论的一个作为当前焦点。

状态字段和更新操作见 [STATE_CONTRACT.md](references/STATE_CONTRACT.md)。Obsidian 导航与笔记约定见 [OBSIDIAN_CONTRACT.md](references/OBSIDIAN_CONTRACT.md)。普通调查不读取脚本源码。

## 分层探索

先进行有限的全景定位，只为识别业务边界、主要入口、关键结果、重要数据和高价值未知，不建立全库对象清单。

随后围绕当前焦点深入：

1. 提出当前最关键的解释或假设。
2. 定向寻找能支持、削弱或推翻它的材料。
3. 追踪真实调用与数据变化，直到足以解释业务行为。
4. 检查例外、反证、语义冲突和运行条件。
5. 更新结论、证据、笔记和调查状态。
6. 判断继续深挖是否还能显著提高核心结论的可信度或解释力。

大文件只读取相关区段。已经形成可靠摘要的内容，不因切换会话而重新全文阅读。没有产生新理解的搜索和文件读取不触发状态更新。

## 业务全链路

从业务视角说明行为如何开始、为什么沿当前路径推进、哪些判断和处理改变了行为或数据，以及最终形成什么结果。实际存在的失败、回退、补偿、异步或跨边界行为也应进入链路；不存在的阶段不要补造。

主链优先写业务含义，源码方法作为实现依据嵌入，并链接到方法详情。例如：

```md
1. 接收业务行为并建立处理上下文
   - 业务作用：……
   - 实现：[[方法明细/相关模块#^m-001|methodA()]]
```

图形只是辅助。即使使用 Mermaid，仍保留一份含 Obsidian 方法链接的文字链路或步骤表。

## 重要字段生命周期

重要字段由其对业务语义、路径或结果的影响决定，而不是由出现次数决定。用户点名的字段默认重要；模型还应发现用户未点名但实际关键的字段。

按真实情况追踪字段从产生到最终消费的过程，包括相关的读取、校验、默认、转换、覆盖、传播、边界传递、持久化或终止使用。只记录实际存在且有意义的变化；普通机械复制可以合并，但不能因此断开生命周期。

每个生命周期节点都链接到具体方法详情。尚未追踪到的位置明确标为待探索，不能用顺滑叙述掩盖断点。

## 方法详情

业务主链中出现的每个实际方法都必须有稳定的 Obsidian 跳转目标。这里指选定业务链路内的方法，不是仓库中的全部方法。

方法详情可以一方法一笔记，也可以按模块、类或主题分组，但每个方法都有独立标题或块 ID。根据实际情况解释：

- 完整签名与源码位置；
- 在当前业务链路中的责任；
- 当前链路里的调用者与后继调用；
- 与业务有关的输入、输出和重要字段影响；
- 会改变行为的条件、效果、异常与特殊路径；
- 支持当前理解的证据、可信度和未确认内容。

简单方法保持简短但说明业务作用；关键方法深入剖析。不要逐行翻译源码。方法详情链接回所属链路、相关字段、调用关系和证据。

## 证据与结论

结论状态使用 `hypothesis`、`supported`、`uncertain`、`contradicted`、`superseded`。源码中存在某个实现不等于实际环境必然执行；缺少运行条件时按证据强度表述。

发现反例或矛盾时，重新打开对应问题并更新旧结论，不维护表面完成状态。详细推理写入 Markdown；JSON 只保留短摘要、状态和笔记引用。

## 状态更新

在以下理解事件发生时调用 `ucef_state_update`：

- 形成或重排关键问题；
- 开始调查新的重点；
- 新证据改变当前理解；
- 问题变成部分明确、已明确、受阻或暂缓；
- 发现新的高价值问题或核心矛盾；
- 子任务返回并被主 Agent 判断合并；
- 结论被推翻或替代。

准备中断、压缩上下文或切换重点前调用 `ucef_state_checkpoint`。状态工具只维护调查控制面，不替模型决定分析内容。

## Obsidian 成果

默认入口为：

```text
分析首页.md
业务全链路.md
字段生命周期.md
方法明细/
证据库.md
调查工作台.md
.ucef/state.json
```

可以根据规模合并或继续拆分，不为目录结构制造空内容。`调查工作台.md` 的状态区由工具同步；其余内容由模型自由组织。所有关键结论、字段和方法通过稳定链接互相跳转。

优先使用用户已有的 Obsidian Skill/MCP 操作笔记；不可用时才使用普通文件工具，并且只能写入选定分析目录。不要生成 HTML。需要对外分享时，HTML 只是 Markdown 的可选导出物，不参与分析。

## 子任务

只有边界清晰、可独立回答的问题才交给 `ucef-probe`。子任务接收一个问题、价值、已知信息、范围和期望证据；返回结论、证据、适用条件、未知项和建议笔记引用。

子任务不修改全局状态和笔记，不生成总报告，也不继续委派。主 Agent 负责处理冲突、合并结论并维护全局视角。

## 校验与完成

只在阶段性整理或交付前调用 `ucef_workspace_validate`，不要每写一段就反复校验。

主要分析完成应满足：

- 用户关心的业务链路已从业务起点解释到结果；
- 关键行为差异能够解释原因和适用条件；
- 重要字段已追踪到最终消费位置，或明确标记无法闭合的断点；
- 主链中每个方法都有可跳转详情；
- 关键结论具有可定位证据；
- 核心矛盾已处理，剩余未知项及其影响清晰可见；
- 读者能够根据笔记预测主要业务行为并定位对应实现。

先更新状态和检查点，再整理分析首页。不要先宣布完成，再检查证据。

## 避免

- 用完整类清单代替业务链路；
- 用调用顺序代替业务解释；
- 用字段出现位置代替字段生命周期；
- 用图形连线代替证据；
- 为固定模板扭曲实际语义；
- 对简单方法过度扩写，对关键方法只做表面概括；
- 没有新增理解时重复搜索、验证或重写；
- 用记录数量代表分析深度。
