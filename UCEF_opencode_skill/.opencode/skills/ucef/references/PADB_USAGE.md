# padb 按需查询策略

`padb` 是用户真实环境中已经安装的数据库查询 Skill。UCEF 只决定何时需要数据库证据以及如何使用结论，不复制 `padb` 的命令、连接或实现说明。

## 何时加载

只有当前高价值问题无法由源码可靠回答，并且数据库事实会改变业务结论时才加载 `padb`，例如：

- 分支取决于当前环境、租户、渠道或时间范围内的有效配置；
- 需要确认表、列、键、关联或持久化映射的真实形态；
- 重要字段的生命周期到达数据库，但来源、覆盖或最终消费仍有断点；
- 需要用必要的业务状态或样本区分多个静态可达路径。

不要为了“更完整”遍历数据库，不要对每个方法查询，也不要用大量样本代替代码语义分析。

## 查询前

先在当前焦点中写清：要回答的唯一问题、为什么源码不足、需要哪个环境/租户/业务键/时间范围，以及什么结果会支持或推翻当前结论。然后加载 `padb`，遵循它自己的使用方法，不猜测命令和返回结构。

查询保持最小化：只选必要列，使用明确过滤条件和合理行数限制；优先元数据、聚合或小样本，避免 `SELECT *`、无界扫描和无关表探索。

## 安全边界

- 默认只读；禁止 INSERT、UPDATE、DELETE、MERGE、DDL、存储过程写操作和生产配置变更。
- 不索取、不展示、不写入 Obsidian 的内容包括密码、令牌、连接串、密钥及与当前问题无关的个人或业务明细。
- 对账号、手机号、证件、地址、订单明细等敏感字段只保留完成判断所需的脱敏摘要。
- 查询可能昂贵、范围不清或权限不足时停止并记录阻塞，不反复改写 SQL 试探。

## 解释结果

区分以下结论强度：

- 表或列存在：只能证明数据库结构；
- 当前存在某配置或记录：证明指定环境与查询时点的数据状态；
- 数据符合某分支条件：支持该路径在指定范围内可能或曾经适用；
- 某次请求实际走过该路径：还需要足够的业务键、时间和因果关联，不能只凭相似记录断言。

数据库结果与源码矛盾时不要强行选边。先检查环境、版本、时间、灰度、缓存、默认值、数据延迟和查询范围，再把冲突保留为待确认问题。

## 写入 Obsidian

只保存可复核且已脱敏的证据摘要：查询目的、环境/快照、数据库对象与列、关键过滤条件、查询时间、结果概括、它支持或反驳的结论，以及必要的来源标识。通常不保存完整结果集，也不把大段 SQL 或表格复制进主链。

查询改变主链、分支判断、字段生命周期或未知项时，局部更新对应笔记和 `调查状态.md`；没有改变理解时不为查询数量制造新笔记。
