# 从探索到可交付业务档案

本参考用于首次接触陌生项目、用户只提出宽泛业务域、建立/更新业务地图、源码版本变化，以及阶段性交付或最终交付。目标是让 UCEF 自己具备稳定、可阅读、可演化的知识产物，而不是依赖外部知识库或把 Markdown 变成数据库。

## 四类根页面及其关系

```text
初始项目扫描
   ↓
<业务域>｜探索地图       候选、未知、优先级
   ↓ 证据提升或降级
<业务域>｜业务地图       已确认链路、跨链路关系、重大演化
   ↓
<业务主题>｜全链路分析入口  一条链路的封面、结论和下钻导航
   ↓
字段、模块、方法、证据与公共知识  细节和稳定复用
```

调查状态不在这条阅读链中竞争位置。它是当前链路的恢复指针，记录“为什么下一步查这里、哪些范围不必重查”，不复制业务正文。

不是每次都要新建四类页面：

- 已存在明确链路和业务地图时，直接恢复链路封面与状态；
- 用户给出明确新链路时，创建或更新业务地图和链路封面；
- 项目陌生、问题宽泛或找不到可信入口时，先创建/更新探索地图；
- 字段、模块、方法只在解释力或复用价值足够时另建笔记。

## 根页面的轻量身份

新建探索地图、业务地图和链路封面时，在开头保留最小 frontmatter，供搜索、恢复和状态判断使用：

```yaml
---
ucef_role: exploration-map # 或 domain-map / chain-cover
business_domain: <实际业务域>
chain: <仅 chain-cover 需要>
knowledge_status: 探索中 # 探索中 / 部分确认 / 可交付 / 需复验
source_snapshot: <项目标识@版本；项目标识@版本>
---
```

frontmatter 只描述页面身份、范围、总体状态和来源快照；不记录事实库存、待办清单或业务正文。已有用户笔记不要求批量补齐，用户改动后读取并尊重现有值。其他方法、字段和证据笔记不强制使用它。

总体状态和结论可信度不是一回事：

- 根页面状态使用“探索中、部分确认、可交付、需复验”；
- 具体结论使用“已确认、较强推断、待确认、需复验、已被反例否定”。

## 有边界的初始项目扫描

初始扫描只回答“接下来该挖什么”，不能变成模块、类、接口或配置的全量盘点。先确认真实项目、模块、版本和业务职责，再以最小检索建立以下候选：

- 可见的业务入口类别，如 HTTP/GRPC、消息消费者、定时任务、批处理、事件订阅或命令入口；
- 可能的业务结果、外部边界、状态变化和持久化边界；
- 可能决定路径的配置、规则、租户、渠道或数据库依赖；
- 值得优先验证的业务链路与它们的业务价值；
- 仍缺失的运行条件、领域术语或材料。

探索地图把“已观察到”“候选链路”“待确认”“已排除范围”和“优先探索”清楚分开。每个候选至少说明它基于什么入口/证据、为什么有业务价值、下一步验证什么；不能用类名、包名或框架注解猜成已确认链路。

范围宽且存在独立问题时，主 Agent 可以并行委派 Probe 分别调查入口类别、异步/外部边界、状态/持久化边界或规则选择条件。Probe 的结果只作为探索地图的观察或候选；主 Agent 审查后才提升。

## 提升、降级与业务域地图

探索地图中的候选在能够识别其业务起点、可能结果或明确业务责任，并有源码或可信材料支持时，提升到业务域地图。业务域地图同时展示：

- 已确认链路及其总体状态和链路封面链接；
- 仍值得继续的候选链路，但显式标为待确认；
- 跨链路复用的关键模块、字段或外部系统；
- 影响多个链路的业务术语、配置条件、状态或风险；
- 重大知识演化与仍未覆盖的边界。

业务地图是长期的业务导航，不是目录清单。新业务域出现第一条真实链路或初始扫描已经形成可行动候选时就建立它；不要等到第二条链路才补建，也不要在没有内容时创建空地图。

反例、源码版本变化、配置条件变化或数据库快照过期时，先判断影响哪些链路和结论。受影响项标为“需复验”并回到探索/待确认，而不是删除历史或将整个业务域重做。确认反例后保留旧结论的变更说明。

## 链路封面

`<业务主题>｜全链路分析入口` 就是链路封面，不另建重复首页。它的首屏应让不了解系统的 Java 开发者看明白：

- 这条业务解决什么问题、从哪里开始、以什么结果结束；
- 当前总体状态、适用范围和来源快照；
- 已确认的主链简述和一张主图（可交付时）；
- 最会改变结果的分支、字段、外部/持久化边界；
- 通往字段、模块、方法、证据和调查状态的链接；
- 仍未知、需复验或可能推翻结论的条件。

首屏是导航和判断层，不粘贴原始 JSON、长 SQL、大段代码、全部字段或方法。信息超过首屏可读范围时下沉到链接笔记；原始材料只在靠近结论的位置以可折叠区保留。章节顺序、主图类型和细节拆分由业务内容决定。

## 业务术语与对象对照

只有当名称歧义会影响主链、字段、分支或跨项目理解时，创建或扩展 `<业务域>｜术语与对象对照`。每条术语按需说明：业务称呼、代码/消息/表字段中的别名、它们是否同一对象、当前业务含义、来源项目/符号，以及相关链路链接。

不要把所有 DTO、字段或枚举写成字典。典型触发包括：同一个“状态”在订单/清算/外部回执中含义不同，同一业务对象跨项目名称不同，或配置/数据库值与代码枚举名称不一致。

## 共享知识与跨链路差异

公共知识只收录可复用的稳定语义：对象职责、输入输出、固有分支、副作用、来源版本和“被哪些链路使用”的紧凑索引。某方法或字段在不同链路中的调用者、参数、命中条件、字段含义和业务结果仍写在各自链路。

第二条链路复用同一对象时，在当前链路写清“本次与历史相同什么、不同什么、仍未确认什么”，再给公共知识增加一条链接。不要为未发生的跨链路比较预建对照表。

## 来源新鲜度、已排除范围与演化记录

每次恢复或阶段性交付时，对照根页面的 `source_snapshot` 与当前 `index-mcp` 项目版本；涉及 `padb` 的事实还要对照查询环境与快照时间。来源未变化时不重复验证；发生变化时只从受影响的项目、符号、配置或结论开始检查。

调查状态的“已检查且无需重复”必须写明范围、结论、证据链接和暂不继续的理由；“下一步精确入口”必须写明业务影响和优先原因。这样恢复时既能知道做过什么，也能知道为什么没有继续扩展。

业务地图只记录重大演化：何时发生了什么知识变化、依据是什么、影响哪些链路/结论、接下来要不要复验。它不记录每次搜索、每个工具调用或机械编辑。

## 一次性质量闭环

阶段性交付或最终交付前，只做一次面向读者的检查：

- 业务地图是否能区分已确认链路、候选和需复验项；
- 链路封面是否说明业务目的、边界、总体状态、主图和下钻入口；
- 高影响结论是否有适用条件、可信度和可回查证据；
- 主图中的关键步骤、判断或状态迁移是否有依据或明确未知；
- 重要字段和术语的断点是否显式；
- 本次新增、修正、推翻或待复验内容是否进入演化记录。

这不是字数、笔记数、图数量或覆盖率评分。发现缺口时记录其业务影响和下一步，不为通过检查而扩大到无关源码。
