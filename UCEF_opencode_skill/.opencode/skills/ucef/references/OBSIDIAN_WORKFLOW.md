# Obsidian 分析与断点工作流

## 唯一分析入口

每次挖掘最初只创建两篇名称明确的笔记：

```text
<业务主题>｜全链路分析入口.md
<业务主题>｜调查状态.md
```

业务主题应让用户不打开文件就能区分本次挖掘；同名场景存在多个系统或范围时，把系统/范围写入名称，不使用难懂的随机 ID。两篇笔记默认可以放在同一目录，但目录不是分析身份，用户可以之后移动它们。

分析入口是本次挖掘的唯一身份和导航页，至少让人看到：调查目标与业务边界、调查状态链接、涉及的源项目及其实际环境映射、当前业务结论，以及通往全链路、字段、模块、方法、图形和未知项的主要链接。具体排版由内容决定，不要求固定表格或空章节。

源项目映射在入口中维护，每个项目记录可读标识、`index-mcp` 中的身份、当前实际根目录、版本/提交和业务职责。正式证据引用项目标识与相对路径；源码目录迁移时只更新入口中的实际根目录。创建真实入口时必须把示例占位符替换成当前环境值；未知项写“未确认”并提出需要用户确认的问题，不能留下“某目录”“可能的项目”等假环境描述。

理解逐渐稳定后再按需要创建业务链路、字段、模块、方法和证据笔记，不预建空目录和空页面。方法较多时可以按模块或类分组，每个方法使用独立块 ID，不必一方法一文件。

每篇属于本次挖掘的内容笔记在开头保留：

```text
归属本次挖掘：[[<业务主题>｜全链路分析入口]]
```

这样入口的反向链接可以识别一次挖掘的全部内容，文件位置和拆分方式仍可自由调整。

## 多链路业务域聚合

新建分析且用户没有指定目录、也不存在可沿用布局时，默认采用下面的分层方式。业务域无法可靠判断时先向用户确认，不把 Git 仓库名直接当作业务域：

```text
<业务域>/
├─ 00-<业务域>｜业务地图.md
├─ 链路/
│  ├─ <链路A>/
│  │  ├─ <链路A>｜全链路分析入口.md
│  │  └─ <链路A>｜调查状态.md
│  └─ <链路B>/...
└─ 公共知识/
   ├─ 方法/
   ├─ 字段/
   └─ 模块/
```

开始第一条链路时只创建实际需要的链路目录、入口和状态；出现第二条链路时再创建业务地图，出现真正可复用的内容时再创建对应公共知识目录，不预建空结构。业务地图只承担导航、链路边界和跨链路关系说明；每条链路仍有自己的入口与调查状态，避免恢复时串线。一条链路跨多个源码项目时仍按业务域聚合，源项目归属由入口中的项目映射表达。

用户指定了其他目录或 Vault 中已有清晰布局时尊重现状，通过 Wikilink 和反向链接维持关系。默认目录解决“人怎么找”，入口链接解决“内容属于哪次挖掘”；移动目录不应让恢复失效。

## 调查状态与恢复胶囊

`<业务主题>｜调查状态.md` 是 Agent 的连续工作记忆，同时保持人类可读：

```md
# <业务主题>｜调查状态

归属本次挖掘：[[<业务主题>｜全链路分析入口]]

## 用户目标
用户最终要理解、判断或解决什么。

## 当前业务边界
从哪里开始，分析到什么业务结果；哪些范围暂不进入。源项目和实际目录以分析入口中的映射为准。

## 已确认的关键结论
- 结论、可信度、[[证据]]和相关笔记。

## 当前业务主链
用紧凑语言描述已经确认的主干，并链接[[<业务主题>｜业务全链路]]。

## 重要字段和模块
- [[<业务主题>｜字段生命周期#字段]]：为什么重要、目前追到哪里。
- [[<业务主题>｜关键模块#模块]]：承担什么业务责任。

## 当前焦点
正在回答的问题、当前假设、已经看到什么、还差什么。

## 待探索
按业务影响和不确定性排序。

## 存疑、矛盾与阻塞
可能推翻结论的反例、缺失材料和影响。

## 下一步精确入口
- 下一次应查看的项目、符号、方法、字段或笔记。
- 为什么先看它，希望验证什么。

## 已检查且无需重复
只写范围、结论和对应笔记，不复制源码。

最近更新时间与当前源码版本/提交标识（如果可获得）。
```

以上十个二级标题是恢复协议的稳定骨架：不要改名、删除或另造近义标题；内容可以自由表达，也可以按业务需要增加三级标题。这样保留 Markdown 的可读性，同时降低多轮会话后的结构漂移。

恢复时先读这份笔记，不重新扫描项目。若源码版本已经变化，只重新验证可能受影响的结论。

恢复后不要机械相信全部摘要。围绕“当前焦点”抽查一至两条最可能影响后续方向的关键证据；抽查失败时降低结论状态并更新待探索项，而不是继续沿用旧判断。

## 写入前自检

每次更新 `调查状态.md` 前快速确认：

- 十个稳定标题仍完整且内容放在正确位置；
- 当前焦点只有一个清楚的问题，下一步入口能直接继续它；
- 新结论已区分确认、推断、待确认或反例，并链接到可回查证据；
- 矛盾没有被顺手覆盖，已检查范围不会导致下一轮重复探索；
- 源码、MCP 返回和数据库结果没有被大段复制进恢复胶囊；
- 使用 `padb` 时已记录环境/快照、范围、时间和脱敏后的证据含义。

这是模型自检清单，不是程序校验器。发现缺项时只修复相关段落，不整篇重写。

## 状态与正式内容解耦

正式内容是用户阅读和修改的知识，调查状态只是恢复指针：

- 状态记录当前焦点、未决问题、已检查范围、下一步和正式内容的 Wikilink，不复制完整正文；
- Agent 不根据状态重新生成或覆盖正式笔记，更新前先读取目标区块并做局部修改；
- 用户的人工改写、重命名和移动视为当前版本，除非证据显示其业务结论需要重新核实；
- 状态和入口不保存内容笔记的绝对路径，通过 Wikilink、反向链接、归属行与块 ID 重定位；
- 链接失效时先搜索并修复引用，不在旧位置重新创建同名笔记；
- 状态丢失时可以从分析入口及其反向链接重建，正式内容不依赖状态文件才能成立。

这层解耦允许用户自由整理笔记，同时保证 Agent 能够恢复；分析身份始终由唯一入口决定，而不是由文件所在目录决定。

## 可选展示层

展示只改善阅读，不决定分析内容。入口、链路、公共知识和状态笔记可以分别添加一个可选样式类：

```yaml
---
cssclasses:
  - ucef-chain
---
```

可用类为 `ucef-entry`、`ucef-chain`、`ucef-shared` 和 `ucef-state`。未安装样式或模型漏写 `cssclasses` 时，笔记仍必须作为普通 Markdown 完整可读，不能把业务信息藏在 CSS 或 HTML 中。

页面采用渐进阅读而非固定模板：开头优先给出当前业务结论、适用范围和最有解释力的图；随后按实际内容展开关键分支、字段、模块和方法；证据与原始材料放在靠近结论的位置，但长 JSON、SQL、代码或查询结果使用 Obsidian 可折叠 Callout：

````md
> [!example]- 原始配置或证据
> ```json
> { "仅保留与结论有关的字段": true }
> ```
````

探索阶段可以暂不画图；完整链路进入阶段性交付或正式交付且证据足够时，至少提供一张主图，类型由模型选择。其他图按解释价值生成，不凑齐图形种类；证据不足时标明缺口。标题顺序和拆分粒度仍由业务内容决定。不要为了视觉整齐制造空章节、同构方法卡片或无证据图形。仓库提供的 `obsidian/ucef.css` 只是可选外观，不参与推理和恢复。

## 笔记状态

使用自然语言和Callout表达状态，不需要JSON：

```md
> [!success] 已确认
> 结论、为什么成立、证据链接。

> [!warning] 较强推断
> 已有依据、尚缺条件、错误时会影响什么。

> [!question] 待确认
> 当前未知和下一步验证入口。

> [!danger] 已发现反例
> 哪条旧结论被推翻以及需要更新哪些笔记。
```

## 稳定下钻

关键块使用短而稳定的ID：

```md
## 方法：methodA(...)

它在当前业务链中的独特作用……

^m-001
```

主链引用：

```md
[[<业务主题>｜相关模块方法明细#^m-001|methodA()]]
```

建议前缀：业务结论 `c-`、调查问题 `q-`、证据 `e-`、字段 `f-`、方法 `m-`、模块 `mod-`。ID只用于导航，不建立实体模型。

## 主链与方法

业务全链路先写业务步骤，再链接实现方法。方法详情至少让读者知道它为何出现在当前链路、改变什么业务行为，以及证据在哪里；其他内容根据方法特点自由展开。

图形旁增加可点击步骤表，避免Mermaid链接在不同环境下表现不一致：

| 业务步骤 | 方法下钻 | 关键字段 | 结论/证据 |
|---|---|---|---|
| …… | [[<业务主题>｜相关模块方法明细#^m-001|methodA()]] | [[<业务主题>｜字段生命周期#字段A]] | [[<业务主题>｜证据#^e-001]] |

## 知识复用

跨链路复用以 Obsidian 链接完成。公共方法、字段或模块笔记首先写清可见的源码身份，例如：

```text
源码身份：clearing-service::com.example.ClearingService#execute(...)
```

同一源码身份的公共笔记主要记录不依赖具体链路的稳定语义、证据版本和紧凑的“被哪些链路使用”索引。当前链路笔记记录这次由谁调用、实际输入、命中条件、字段语义、业务结果，以及相对历史链路的相同点和不同点，并链接公共笔记；不要把所有链路叙述复制进公共笔记。

遇到历史知识时：先按源码身份和业务别名检索，读取稳定摘要与相关链路区块，再用 `index-mcp` 核验当前版本。实现未变的稳定语义可以复用；调用上下文、配置、分支或结果不同的部分必须在当前链路重新解释。无法确认是否同一对象或是否稳定时不合并，先留在当前链路；第二条链路再次遇到或已有充分源码证据时再提升为公共知识。
