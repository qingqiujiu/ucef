# UCEF 持续开发版 for OpenCode

`UCEF_opencode_skill/` 是随Git持续更新的唯一开发目录。历史 `UCEF_opencode_skill_v*` 和发布包只作为快照保留，后续修改不再创建新的版本文件夹。

本版没有自定义 Runtime、Python脚本、SQLite、JSON提交协议或HTML生成器。UCEF是一套强业务分析提示词，直接使用已经安装的 `index-mcp` 与 `obsidian-mcp`：前者提供源码事实，后者承载持续笔记、图形与断点恢复；遇到源码无法确认的数据库问题时，按需加载用户已有的 `padb` Skill。

## 安装内容

将 `.opencode/` 合并到OpenCode控制目录，或直接把本目录作为控制项目：

```text
UCEF_opencode_skill/
├── .opencode/
│   ├── agents/
│   │   ├── ucef-java-chain.md
│   │   └── ucef-probe.md
│   └── skills/
│       └── ucef/
│           ├── SKILL.md
│           └── references/
└── obsidian/
    └── ucef.css              可选外观
```

后续在仓库中更新 Git 即可得到同一路径的新内容。如果使用复制方式安装，核心能力只需同步 `.opencode/` 到原控制目录；已经启用可选外观时再同步 `obsidian/ucef.css`，不要创建新的版本号目录。

## 前置能力

- `index-mcp`：能够定位符号、定义、实现、引用、调用关系和精确源码区段；
- `obsidian-mcp`：能够搜索、读取、创建和局部更新笔记，并支持Wikilink、块引用与Mermaid；
- `padb`（可选）：能够按自身说明只读查询数据库，用于必要的配置、元数据和运行数据佐证；
- 如果 `obsidian-mcp` 只读，需要已有 Obsidian Skill/CLI 提供写入能力；
- Obsidian Vault中的一个分析目录；
- 一个或多个由 `index-mcp` 能够识别的只读源项目。分析位置不必位于任何源项目目录中。

主 Agent 使用 `permission: allow`，以适配真实环境中的 MCP、Skill、Obsidian CLI 与子 Agent。开放权限只解决工具调用，不改变安全边界：源码项目和数据库默认只读，正式写入只发生在用户确认的 Obsidian 位置。

Probe 仍只允许：

```text
skill
index-mcp_*
```

若 `index-mcp` 注册名不同，只修改 Probe 的权限前缀。不要为匹配名称重新包装一层 UCEF 工具。

## 启动

选择 `ucef-java-chain`，给出：

- Obsidian分析目录或目标Vault位置；
- 本次挖掘的清晰业务名称；
- 源码范围；
- 用户真正关心的业务问题；
- 已知入口、重点字段或限制条件（如果有）。

示例：

```text
使用 ucef-java-chain 分析这项业务。
本次挖掘命名为“清算通知任务”，分析笔记写入 Obsidian 的 UCEF/清算通知任务。
源码通过当前 index-mcp 只读访问；请识别实际相关项目并记录项目映射，有歧义时询问我。
需要数据库事实时加载 padb，并严格保持只读和最小范围。

请从业务视角解释完整链路、关键分支为什么发生、重要字段的完整生命周期，
识别关键模块，并让主链中的每个方法都能跳转到详细笔记。
根据真实关系生成有助于理解的时序图、流程图、状态图、ER图或字段流转图；
无法确认的运行条件和关系明确保留为未知。
```

主 Agent 会查找 `清算通知任务｜全链路分析入口.md`。已有分析从入口链接的调查状态继续；新分析先创建同主题入口和状态，再随着理解增加笔记。当前工作目录不会被当成分析位置或唯一源码范围。

开始大规模检索前，主 Agent 会先确认 Obsidian 确实存在可写路径，避免分析结果只停留在易丢失的聊天上下文中。

## 推荐笔记

不要求一次性创建完整目录。最终通常包括：

```text
<业务主题>｜全链路分析入口.md
<业务主题>｜调查状态.md
<业务主题>｜业务全链路.md
<业务主题>｜字段生命周期.md
<业务主题>｜关键模块.md
<业务主题>｜<模块>方法明细.md
<业务主题>｜证据.md
```

这些是阅读入口，不是必须填满的输出Schema。内容规模和拆分方式由模型根据实际业务决定。

用户没有指定目录且不存在可沿用布局时，默认使用 `<业务域>/链路/<当前链路>/` 放置专属内容。出现第二条链路时再建立 `<业务域>｜业务地图.md`，出现真正共享的内容时再建立“公共知识”目录，不预建空结构。目录负责阅读整理；每条链路仍以自己的入口和状态为身份，跨项目链路不按 Git 仓库拆散。

遇到以前分析过的方法、字段或模块时，主 Agent 会先按源项目与完整符号检索旧笔记并核验源码版本。对象自身不随链路变化的部分进入公共知识，当前调用者、参数、命中分支、字段含义和业务结果留在当前链路。拿不准时先不抽象，避免较弱模型错误合并。

## 可选 Obsidian 外观

将 `obsidian/ucef.css` 复制到目标 Vault 的 `.obsidian/snippets/ucef.css`，然后在 Obsidian“外观 → CSS 代码片段”中启用。笔记可使用 `ucef-entry`、`ucef-chain`、`ucef-shared` 或 `ucef-state` 作为 `cssclasses`。

CSS 只调整标题、内容宽度、Callout、表格和链接外观。未安装、未启用或没有添加样式类时，全部笔记仍是完整可读的标准 Markdown，不影响模型分析与断点恢复。

完整链路进入阶段性交付或正式交付且证据足够时，默认至少有一张解释主链的主图；流程图、时序图、状态图、ER 图、字段图等其他图形只按实际价值增加，不要求凑齐。

## 更新与迁移

Skill更新只需要Git拉取或重新同步 `.opencode/`。分析成果始终留在Obsidian中，不受Skill目录更新影响。

用户可以移动或重命名正式内容；保留其“归属本次挖掘”Wikilink，并让 Obsidian 更新链接。源码项目迁移时只更新分析入口中的“项目标识 → 实际根目录”映射，不需要重写全部证据。调查状态只保存恢复指针，不作为正式内容的副本。

旧版SQLite/HTML工作区不会自动转换。需要复用时，将真正有价值且能够重新验证的结论链接或迁入Obsidian；不要把旧实体库存整体导入。
